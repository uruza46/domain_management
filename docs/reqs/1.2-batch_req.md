# バッチ処理要件

*作成日: 2026/06/05 ／ 親: [1-funk_req.md](1-funk_req.md)*

---

## 1. 本ドキュメントの位置づけ

本ドキュメントは、画面操作によるオンライン処理を補完する定期実行ジョブを定義する。本システムの中核は「情報収集の自動化」であり（[0-base_req.md](0-base_req.md) 0.2）、バッチは自動収集・自動チェック・通知の主たる担い手となる。各機能からバッチへ引き渡すイベント、バッチの抽出条件、実行順序、冪等性、通知・エラー処理を扱う。

画面上の表示項目や入力エラーは [1.1-screen_req.md](1.1-screen_req.md) に記載する。機能の目的やロール制御の概要は [1-funk_req.md](1-funk_req.md) に記載する。

外部連携は初期段階ですべてを必須とせず、手動登録・CSV 取込・定期バッチ・自動 API 連携を段階的に選択できるものとする（[0-base_req.md](0-base_req.md) 0.11）。本ドキュメントの自動収集バッチは、連携先が未整備の段階では手動登録・CSV 取込で代替できることを前提とする。

## 3. オンライン処理からバッチへの連動要件

| オンライン処理 | バッチ連動 |
|----------------|------------|
| F03 ドメイン新規登録 | `pending` で保存する。承認（F15）後に B01/B02 の収集対象になる |
| F05 ドメイン情報編集 | 手動更新値を正とし、B01/B02 は手動上書き項目を尊重して差分のみ記録する |
| F06 廃止 | 廃止確定後、B01〜B04 の収集・チェック対象から除外する |
| F07 管理責任・継承設定 | 継承元・管理責任部署の変更を B07/B08 の通知先・棚卸対象に反映する |
| F08 棚卸回答 | 最終棚卸日・次回確認期限を更新し、B08 の起票・督促判定に反映する |
| F09 是正対応 | 対応期限・状況を B07 の督促判定に反映する |
| F15 承認 | 取得・移管・管理責任者変更の確定を B01/B02/B07 の対象・通知先に反映する |

画面処理はドメイン情報・管理責任・確認状態を正として記録する。自動収集による値の変化は、手動上書き項目を尊重しつつ差分として履歴に残す。

## 4. B01: WHOIS・登録情報収集

### 目的

レジストラ・登録情報を定期取得し、有効期限・更新期限の見落としによる失効リスクを低減する（[0-base_req.md](0-base_req.md) 0.5.1, 0.5.2）。

### 実行スケジュール

- 毎日 02:00（JST）

### 抽出条件

1. `domains.status = 'active'`
2. 種別が gTLD / ccTLD（登録ドメイン）であるもの
3. 廃止済み（`deleted`）は対象外

### 処理内容

1. 対象ドメインの WHOIS / RDAP を取得する。
2. ドメイン名、種別、状態、登録日、有効期限、更新方針、レジストラ名、契約名義、更新期限、更新通知先、ネームサーバを抽出する。
3. 台帳の自動収集項目と差分を検出し、手動上書きされていない項目を更新する。
4. 差分は `change_type = '自動収集更新'` として変更履歴に記録する（変更がない間は圧縮し、新規差分のみ記録）。
5. 取得できなかった・名前解決できないドメインは警告ログを出し、失効・移管の疑いとして B07 の通知候補にする。

### パラメータ

| パラメータ | デフォルト | 説明 |
|------------|------------|------|
| `WHOIS_RATE_LIMIT` | レジストラ別 | レジストラ／レジストリのレート制限に従う |
| `BATCH_SIZE` | 200 | 1 実行あたりの処理件数上限 |

## 5. B02: DNS 情報収集

### 目的

DNS 設定を定期取得し、用途把握・リスク評価・サブドメイン検知の基礎情報を最新化する（[0-base_req.md](0-base_req.md) 0.5.3, 0.7.3）。

### 実行スケジュール

- 毎日 02:30（JST）
- B01 完了後に実行すること

### 処理内容

1. 対象ドメイン・DNSゾーンのネームサーバを確認する。
2. 主要レコード（A、AAAA、CNAME、MX、NS、TXT）を取得する。
3. メール関連設定（SPF、DKIM、DMARC）と DNSSEC 設定状況を取得する。
4. CNAME 等で検知した新規サブドメインを管理対象候補として登録し、責任継承ルールで管理情報を継承させる（個別管理対象への昇格は F07 で判断）。
5. 台帳との差分を検出し、手動上書きされていない項目を更新、`自動収集更新` として履歴に記録する。
6. DNS 設定変更は事前承認対象外のため、検知した変更は事後確認・差分記録・是正依頼の対象とする（[0-base_req.md](0-base_req.md) 0.6.3, 0.8）。

### 注意事項

- 複数 DNS 管理サービスを併用する場合、自動取得できない項目は手動管理を併用する。
- 検知したサブドメインは原則として管理対象に含めるが、個別管理対象への自動昇格は行わない。

## 6. B03: 証明書・CT ログ監視

### 目的

CT ログを監視し、台帳未把握の証明書発行を検知するとともに、証明書の有効期限・失効を追跡する（[0-base_req.md](0-base_req.md) 0.5.7）。

### 実行スケジュール

- 毎日 03:00（JST）

### 処理内容

1. 管理対象ドメイン・サブドメインに対する CT ログ発行履歴を取得する。
2. 発行先ドメイン、発行者、有効期限、SAN を抽出する。
3. 台帳の証明書情報と突合し、未把握の証明書発行を検知する。
4. 未把握証明書は証明書台帳（F11）へ登録し、サブドメインテイクオーバー・不正発行の疑いとしてリスク（F09）候補にする。
5. 有効期限が接近・超過した証明書を検出し、B07 の通知対象、セキュリティ対策状況（F10）の更新対象にする。

### パラメータ

| パラメータ | デフォルト | 説明 |
|------------|------------|------|
| `CERT_NOTICE_DAYS_BEFORE` | 30 | 有効期限 N 日前から通知 |

## 7. B04: セキュリティ対策状況チェック

### 目的

セキュリティ対策状況を自動判定し、未実施・不備をリスクとして是正対応に接続する（[0-base_req.md](0-base_req.md) 0.5.6, 0.7.4）。

### 実行スケジュール

- 毎日 03:30（JST）
- B02 / B03 完了後に実行すること

### チェック内容

| 項目 | 判定 |
|------|------|
| DNSSEC 設定状況 | DNSゾーンに DNSSEC が設定されているか |
| レジストリ／レジストラロック | ロックされているか（取得可能な範囲で） |
| サブドメインテイクオーバー | CNAME 等で外部サービスを参照しているが、参照先が未割当・削除済みでないか |
| 期限切れ証明書 | 有効期限切れ・失効予定の証明書が利用されていないか（B03 連携） |
| メールなりすまし対策 | SPF / DKIM / DMARC が設定されているか（B02 連携） |

### 処理内容

1. 上記項目を自動判定し、セキュリティ対策状況（F10）を更新する。
2. 未実施・不備の項目をリスク（F09）として起票し、重大度を付与する。
3. 既に起票済みで解消されたリスクは解消として記録する。
4. テイクオーバー・なりすまし・期限切れ証明書等の重大リスクは B07 の通知対象にする。

### 注意事項

- MFA 設定状況など外部アカウント側でしか確認できない項目は自動判定対象外とし、棚卸・手動確認で扱う。
- 証明書発行・テイクオーバーリスク検知のみを理由とした個別管理対象への自動昇格は行わない（[0-base_req.md](0-base_req.md) 0.4.3）。

## 8. B05: 類似・なりすましドメイン監視

### 目的

自社ブランド名・サービス名・商標・略称等を含む候補ドメインを検知し、監視対象として取り込む（[0-base_req.md](0-base_req.md) 0.3.1, 0.9）。

### 実行スケジュール

- 毎週月曜 04:00（JST）

### 処理内容

1. 監視対象キーワード（ブランド・商標・略称等）をもとに、類似ドメイン・なりすましドメインを探索する。
2. タイポスクワッティング、同形異字、TLD 違い等のパターンで候補を生成・検知する。
3. 検知した候補を監視対象（F12）として登録し、検知種別・関連ブランド・登録情報（WHOIS）を付与する。
4. 既知の自社保有ドメイン・既存監視対象は重複登録しない。
5. 新規検知・状況変化のある候補を B07 の通知対象にする。

### 注意事項

- 監視頻度、対象キーワード、対応フローは運用にあわせて確定する（[0-base_req.md](0-base_req.md) 0.14）。
- 監視対象は保有・契約・DNS 等の必須管理項目を持たず、検知結果・確認状況・対応判断・対応履歴のみ管理する。

## 9. B06: ライフサイクル状態自動遷移

### 目的

日付・有効期限の経過に応じて `domains.status` を自動更新し、後続の通知・棚卸判定の入力を整える（[0-base_req.md](0-base_req.md) 0.6）。

### 実行スケジュール

- 毎日 01:00（JST）
- B07 より前に完了すること
- 手動実行可能であること

### 処理内容

| ステップ | 対象 | 遷移 |
|----------|------|------|
| 1 | `status = 'active'` かつ 有効期限超過かつ 更新確認なし | `expired`（失効疑い） |
| 2 | 廃止確定済みの一時保持 | `deleted` |

### 履歴

- 各遷移ごとに `change_type = 'ステータス変更'` を変更履歴に記録する。
- `diff_json` には変更前後の status を含める。
- 失効疑いへの遷移は B07 の通知対象にする。

### 実行基盤

- Django management command として実行できること。
- 本番環境では EventBridge Scheduler が起動する ECS Scheduled Task として定期実行できること。

## 10. B07: 通知・アラート送信

### 目的

期限接近・リスク・棚卸・承認滞留を関係者に通知し、見落としを防ぐ（[0-base_req.md](0-base_req.md) 0.9）。

### 実行スケジュール

- 毎日 09:00（JST）
- B01〜B06 完了後に実行すること

### 通知対象（[0-base_req.md](0-base_req.md) 0.9）

| # | 事象 | 抽出条件 |
|---|------|----------|
| 1 | ドメイン更新期限の接近 | 有効期限／更新期限が N 日以内（既定 30 日） |
| 2 | 証明書有効期限の接近 | 証明書有効期限が N 日以内（既定 30 日、B03 連携） |
| 3 | 担当者未設定・情報陳腐化 | 管理責任者未設定、または最終棚卸日が一定期間超過 |
| 4 | DNS 設定の不整合・危険な設定 | B04 が検出した DNS 設定不備 |
| 5 | サブドメインテイクオーバーの可能性 | B04 が検出したテイクオーバー疑い |
| 6 | DNSSEC・DMARC 等の未設定 | B04 が検出した重要対策未設定 |
| 7 | 類似・なりすまし・ブランド毀損の検知 | B05 が検知した候補ドメイン |
| 8 | 棚卸未回答・是正期限超過・承認滞留 | B08 の未回答、F09 の期限超過、F15 の滞留 |

### 通知仕様

| 項目 | 内容 |
|------|------|
| 送信先 | 対象管理単位の管理責任部署・主担当（継承元を含む）、重大事象は管理責任者・セキュリティ運用 |
| 連絡先 | 個人メールではなく、可能な限りグループメール／チーム連絡先 |
| 件名 | `【ドメイン管理】<事象種別> (YYYY/MM/DD)` |
| 本文 | 対象ドメイン・管理単位、事象内容、期限、対応導線 |
| 送信条件 | 対象が 1 件以上ある場合のみ |
| エスカレーション | 未回答・期限超過が一定期間続く場合、管理責任者・上位部署へエスカレーション |

### 冪等性

- 同一事象・同一対象への同日重複通知を行わない。
- 通知済みフラグまたは送信履歴で重複送信を抑止する。

## 11. B08: 棚卸起票・督促

### 目的

定期棚卸（原則年 1 回）と都度確認を起票し、未回答・期限超過を督促・エスカレーションする（[0-base_req.md](0-base_req.md) 0.7.2）。

### 実行スケジュール

- 起票: 年次（棚卸サイクル開始日）
- 督促: 毎日 09:30（JST）、B07 と整合させる

### 処理内容

**定期棚卸の起票**

1. 管理対象ドメインおよび個別管理対象のサブドメイン名前空間を対象に、棚卸を起票する。
2. 個別管理対象でないサブドメインは、上位管理単位の棚卸に含めて代表確認とし、全件個別起票しない。
3. 確認状態を「確認依頼中」、次回確認期限を設定する。

**都度確認の起票**

1. B01〜B05 が検知した差分・リスク・用途変化・外部連携変化のうち、確認が必要なものを都度確認として起票する。
2. 対象管理単位の管理責任部署・主担当に確認依頼する。

**督促・エスカレーション**

1. 未回答・期限超過の棚卸／都度確認を抽出する。
2. 管理責任部署・主担当へ督促する（B07 経由）。
3. 一定期間超過した場合、管理責任者・上位部署・全社ドメイン管理部門へエスカレーションする。

### 履歴

- 起票・回答・差戻し・是正要否を記録する。
- 確認状態（確認済 / 確認依頼中 / 未回答 / 差戻し / 要是正 / 廃止候補）を更新する。

## 12. B09: 組織・社員・所属・IT資産マスタ同期

### 目的

組織・社員・所属情報および IT 資産情報を定期取得し、管理責任部署・担当者・連携情報を最新状態に保つ（[0-base_req.md](0-base_req.md) 0.5.8, 0.11）。

### 実行スケジュール

- 毎日 03:00（JST）

### 処理内容

1. ID 管理・組織マスタ・社員マスタ・所属マスタから部署・社員・所属情報を取得し、upsert する。
2. 異動・退職により無効化された担当者が、管理責任者・主担当・副担当として残っている場合は警告ログを出し、担当者不在リスク（F09）・通知（B07）の対象にする。
3. IT 資産管理システムと連携し、ドメインと他 IT 資産情報の整合性を確認する。

### 注意事項

- 連携方式は各システム側と調整して確定する。
- 現フェーズでは手動 seed / 手動メンテナンスを併用する。
- 機密情報そのものは取得せず、保管先・管理責任者のみを扱う（[0-base_req.md](0-base_req.md) 0.3.2）。

## 13. B10: 監査ログエクスポート

### 目的

変更履歴を月次で CSV にエクスポートし、監査対応に備える（[0-base_req.md](0-base_req.md) 0.10）。

### 実行スケジュール

- 毎月 1 日 01:30（JST）

### 処理内容

1. 前月分の変更履歴を取得する（手動変更・自動収集更新の双方を含む）。
2. CSV 形式でファイル出力する。
3. 完了後に管理者へ通知する。

### 出力ファイル

```text
domain_audit_log_YYYYMM.csv
```

### 出力列

`target_id, target_type, change_category, change_type, changed_at, changed_by, source, diff_json, note`

## 14. 共通仕様

| 項目 | 内容 |
|------|------|
| タイムゾーン | JST（Asia/Tokyo） |
| 実行基盤 | Django management command。本番は EventBridge Scheduler 起動の ECS Scheduled Task で定期実行 |
| 実行順序 | B01 → B02 → B03 → B04 → B06 → B08 → B07（収集・判定後に通知）。B05/B09/B10 は独立スケジュール |
| 操作者 | バッチによる変更はサービスアカウントを操作者として履歴に記録する |
| 実行ログ | 開始時刻、終了時刻、対象件数、成功件数、失敗件数、検知差分件数 |
| エラー時 | エラーログ出力、管理者通知、必要に応じて次回再試行 |
| 冪等性 | 同じバッチを再実行しても二重登録・二重通知・二重起票にならない |
| 手動上書きの尊重 | 自動収集は手動上書きされた項目を上書きせず、差分のみ履歴に残す |
| レート制限 | WHOIS / RDAP / CT ログ / 外部 API のレート制限・利用規約に従う |
| Secret | 外部 API 認証情報は環境変数または Secret で管理し、コードに埋め込まない |
| 機密情報 | 証明書秘密鍵・DNS 管理アカウント認証情報そのものは取得・保持しない |
| 履歴の圧縮 | 変更がない間の情報は圧縮し、差分が発生した時点のみ履歴を記録する |
