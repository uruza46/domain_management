## 2. 性能要件

| 指標 | 目標値 | 備考 |
|------|--------|------|
| ページ初期表示 | 2秒以内 | ネットワーク遅延除く |
| 一覧検索（htmx 部分更新） | 1秒以内 | サーバー側ページング 50 件単位 |
| フォーム保存（APIレスポンス） | 3秒以内 | |
| ダッシュボード集計（APIレスポンス） | 3秒以内 | 期限・リスク・棚卸・承認の集計 |
| 同時利用ユーザー数 | 30名程度 | 社内利用のため大規模アクセスなし |
| 自動収集バッチ（B01/B02） | 管理対象全件を実行ウィンドウ内で完了 | レート制限に従い分割実行可 |

- 数万件規模のサブドメインを管理対象に含む可能性があるため（[0-base_req.md](0-base_req.md) 0.4.1）、一覧・検索はサーバー側ページングとインデックス（[2-data_design.md](2-data_design.md) 参照）で応答性を確保する。
- 全件への個別問い合わせを避け、差分・例外のみを確認対象とする業務設計（[1-funk_req.md](1-funk_req.md) 5-1）により、棚卸・確認の負荷を抑制する。

## 3. 可用性・信頼性

| 項目 | 要件 |
|------|------|
| 稼働時間 | 平日 08:00〜20:00（社内業務時間） |
| 計画外停止 | 月 1回・4時間以内 |
| データバックアップ | 日次（前日分 DB バックアップを取得） |
| バックアップ保持期間 | 直近 30日分 |
| 障害時 RTO | 翌営業日中の復旧を目標 |
| 障害時 RPO | 前日バックアップ時点（最大 24時間分のデータ損失許容） |
| 自動復旧 | コンテナ／ジョブの異常終了時は実行基盤の再起動・リトライで自動復旧を図る（[0-base_req.md](0-base_req.md) 0.12.8） |
| バッチ再実行 | 自動収集・通知バッチは冪等であり、失敗時に再実行しても二重登録・二重通知を起こさない（[1.2-batch_req.md](1.2-batch_req.md) 14） |

- データのバックアップとリストアが可能であること（[0-base_req.md](0-base_req.md) 0.12.7）。

## 5. データ正確性・管理性

[0-base_req.md](0-base_req.md) 0.12 の要件に対応する。

| 項目 | 要件 |
|------|------|
| 入力必須・未確認状態 | 入力必須項目、更新期限、未確認状態を管理できること（0.12.1） |
| 重要期限の可視化 | 更新期限・証明書期限・棚卸期限を見落としにくいよう、ダッシュボード・通知で可視化すること（0.12.4） |
| 監査証跡 | 監査証跡を保持し、必要に応じて出力できること（0.12.3、[2-data_design.md](2-data_design.md) domain_histories） |
| 自動収集の追跡 | 自動収集による値の変化を、取得元・取得日時とともに履歴へ記録すること |
| 手動上書きの尊重 | 自動収集は手動上書きされた項目を上書きしないこと |
| 機密情報の非保持 | 機密情報そのものは保持せず、保管先・管理責任者のみを管理すること（0.12.6） |

## 6. スケーラビリティ

- 管理対象は登録ドメイン数百件に加え、検知サブドメインが数万件規模に達する可能性を前提とする（[0-base_req.md](0-base_req.md) 0.4.1）。
- 管理責任は管理単位（登録ドメイン・DNSゾーン・サブドメイン名前空間）に集約し、サブドメイン全件に個別の管理責任・棚卸を設定しない継承モデルでスケールさせる。
- 自動収集バッチは対象を分割し、外部サービスのレート制限内で並列・分割実行できる設計とする。
- 本部追加・ブランド追加・会社追加はマスタ変更のみで対応できる設計とする（固定値に依存しない）。
- ユーザー数・データ量増加時は、ECS Fargate のタスク数・スペックと RDS のスペック調整で対応する想定。

## 8. 国際化・多言語

- フェーズ1 は日本語のみ対応。
- 多言語対応は将来検討。
- 日付フォーマット: `YYYY/MM/DD`（日本標準）。
- タイムゾーン: JST（Asia/Tokyo）固定。
- ドメイン名は IDN（国際化ドメイン名）を Punycode で正規化して保持する。

## 9. クラウドデプロイ要件

クラウド構成の詳細は [3.1-cloud_deploy_req.md](3.1-cloud_deploy_req.md) に定義する。

### 本番構成（AWS）

| 項目 | 要件 |
|------|------|
| 実行基盤 | ECS Fargate（Web サービス）+ ALB + CloudFront + RDS PostgreSQL 16 + ECR + Secrets Manager |
| バッチ起動 | EventBridge Scheduler から ECS Scheduled Task を定期起動（B01〜B10） |
| コンテナ実行 | Gunicorn + WhiteNoise を本番実行方式とし、Django `runserver` は本番利用しない |
| 環境変数 | `DJANGO_DEBUG`, `DJANGO_ALLOWED_HOSTS`, `DJANGO_CSRF_TRUSTED_ORIGINS`, `DJANGO_SECRET_KEY`, `DATABASE_URL` を使用 |
| Secret | `DJANGO_SECRET_KEY`, `DATABASE_URL`, 外部 API 認証情報は AWS Secrets Manager から注入する |
| IaC | Terraform で AWS リソースを管理（`terraform/aws/`） |
| ローカル開発 | Docker Compose（web / db / adminer）を継続利用する |

### セキュリティ・運用

| 項目 | 要件 |
|------|------|
| ログイン試行制限 | `django-axes 6.x` により 5 回失敗でアカウントロック |
| ロック解除 | Django admin 画面または `axes_reset` management command で解除 |
| ブルートフォース対策 | `AxesMiddleware` を `SecurityMiddleware` の直後に配置すること |
| 外部送信制御 | 自動収集の外部アクセス先（WHOIS / DNS / CT ログ / 連携 API）は許可先を限定し、SSRF を防ぐ |

セキュリティ要件の詳細は [4-sec_req.md](4-sec_req.md)、脆弱性診断は [4.1-vuln_scan.md](4.1-vuln_scan.md) に定義する。
