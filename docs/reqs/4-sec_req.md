# セキュリティ要件

*作成日: 2026/06/05 ／ 親: [0-base_req.md](0-base_req.md)*

---

## 1. 概要

本システムは、企業の公開ドメインという重要 IT 資産を管理し、ブランド保護・セキュリティ対策の状況を扱う。ドメインのリスク（テイクオーバー、なりすまし、失効等）に関する情報を集約するため、情報自体の保護に加え、システムが自動収集のために外部へ行うアクセスの安全性も確保する。

本システムは機密情報そのもの（証明書秘密鍵、DNS 管理アカウント認証情報等）を保持せず、保管先と管理責任者のみを管理する（[0-base_req.md](0-base_req.md) 0.3.2, 0.12.6）。

## 2. 認証要件

| 要件 | 内容 |
|------|------|
| 認証方式 | Django 標準ローカル認証（ユーザー名・パスワード）を採用。LDAP / SAML SSO は将来検討 |
| セッション管理 | セッショントークンはサーバー側で管理し、クライアント側に平文保存しない |
| セッションタイムアウト | 無操作 30分でセッション無効化 |
| ログアウト | 明示的なログアウト操作でサーバー側セッションを破棄 |
| パスワードポリシー | 社内ポリシーに準拠（8文字以上・英数字混在等） |
| 多要素認証 | 将来検討（フェーズ1 では必須としない） |
| API 認証 | サービスアカウントはハッシュ化サービストークン（`Authorization: Token`）で認証する（[2-data_design.md](2-data_design.md) api_servicetokens） |

## 4. 入力値検証・出力エスケープ

| 項目 | 要件 |
|------|------|
| 入力値バリデーション | すべてのフォーム入力はサーバー側でバリデーションを実施する |
| ドメイン名検証 | FQDN は形式検証し、IDN は Punycode に正規化して保持する |
| SQLインジェクション対策 | ORM またはプリペアドステートメントを使用し、生 SQL への動的値埋め込みを禁止 |
| XSS 対策 | HTML 出力時は必ずエスケープする（テンプレートエンジンの自動エスケープを活用） |
| CSRF 対策 | 状態変更を伴うリクエスト（POST / PUT / DELETE）には CSRF トークンを使用 |
| htmx CSRF | htmx の POST は `base.html` の `htmx:configRequest` で `X-CSRFToken` ヘッダーを自動付与する |
| JS DOM 操作の XSS 対策 | 動的 HTML 生成では `innerHTML` への信頼できない文字列注入を禁止し、`textContent` / DOM API を使用する |
| CSV 取込・出力 | 取込は全行検証後に登録。出力時は Excel 数式として解釈される値を無害化する |
| ファイルアップロード | CSV のみ対象とし、拡張子・MIME タイプ・サイズを検証する |

## 5. 外部アクセス（自動収集）の安全性

本システムは WHOIS / DNS / CT ログ / 連携 API へ外部アクセスを行う。これらは SSRF・不正応答の経路になり得るため、以下を要件とする。

| 項目 | 要件 |
|------|------|
| 接続先の限定 | 自動収集の接続先は許可リスト（レジストラ / DNS リゾルバ / CT ログ API / 連携 API）に限定する |
| SSRF 対策 | 収集対象ドメイン名・URL をもとに内部ネットワーク・メタデータエンドポイントへアクセスしない。名前解決結果が内部 IP を指す場合は遮断する |
| 応答の検証 | 外部応答（WHOIS / DNS / 証明書）はパース時にサイズ・形式を検証し、過大・不正な応答を拒否する |
| 認証情報 | 連携 API の認証情報は Secret Manager で管理し、コード・ログに埋め込まない |
| レート制限 | 外部サービスのレート制限・利用規約に従い、収集を分割・調整する |

## 6. 通信セキュリティ

| 要件 | 内容 |
|------|------|
| 通信暗号化 | HTTPS（TLS 1.2 以上）を使用する |
| HTTP → HTTPS リダイレクト | HTTP アクセスは HTTPS へ強制リダイレクト |
| セキュリティヘッダー | `Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`, `Content-Security-Policy` を付与 |

## 7. データ保護

| 要件 | 内容 |
|------|------|
| 機密情報の非保持 | 証明書秘密鍵・DNS 管理アカウント認証情報そのものは保持しない。保管先・管理責任者のみを管理する（[0-base_req.md](0-base_req.md) 0.3.2, 0.12.6） |
| 個人情報の最小化 | 担当者情報は業務上必要な項目（氏名・連絡先）のみ収集する。連絡先はグループメール／チーム連絡先を推奨 |
| 保存データの暗号化 | RDS の保存領域暗号化を利用する |
| ログへの機密・個人情報出力 | アプリケーション・バッチログに認証情報・個人情報を出力しない |
| バックアップの保護 | バックアップはアクセス制限されたストレージに保存する |
| データ廃棄 | 論理削除データの物理削除ポリシーを別途定義する（例: 論理削除から5年後） |

## 8. 監査ログ要件

| 項目 | 内容 |
|------|------|
| 記録対象 | ドメイン・管理責任・DNS・証明書・リスク・承認の登録／更新／削除、自動収集更新、ログイン／ログアウト |
| 記録内容 | 操作日時・操作者（バッチはサービスアカウント）・操作種別・変更前後の値・取得元 |
| 保持期間 | 3年間（コンプライアンス要件に基づく） |
| 改ざん防止 | 変更履歴・監査ログの更新・削除を禁止する（追記専用、[2-data_design.md](2-data_design.md) domain_histories） |
| 過去時点の追跡 | 過去時点の担当者・利用目的・承認状態・リスク状態を追跡できること（[0-base_req.md](0-base_req.md) 0.10） |
| エクスポート | 月次で CSV エクスポート（B10 バッチ参照） |

## 9. インシデント対応

| 項目 | 内容 |
|------|------|
| 不正アクセス検知 | ログイン失敗 5回以上で `django-axes` によりアカウントロック。ロック解除は Django admin（`/admin/axes/`）または `python manage.py axes_reset` |
| ブルートフォース対策 | `AxesMiddleware` を `MIDDLEWARE` の `SecurityMiddleware` 直後に配置する |
| ドメインインシデント | テイクオーバー・なりすまし・失効等のドメイン起因インシデントはインシデント管理（F13）に記録し、リスク・是正対応へ接続する |
| インシデント報告 | システム／セキュリティインシデント発生時はセキュリティ運用担当者へ即時報告する |

## 11. クラウド環境セキュリティ要件

本番環境（AWS ECS Fargate）の共通セキュリティ要件。詳細は [3.1-cloud_deploy_req.md](3.1-cloud_deploy_req.md) に定義する。

| 項目 | 要件 |
|------|------|
| Runtime Secret | `DJANGO_SECRET_KEY` / `DATABASE_URL` / 外部 API 認証情報は AWS Secrets Manager から ECS タスク定義で注入する |
| Django 本番設定 | `DJANGO_DEBUG=False` を必須とし、`DJANGO_ALLOWED_HOSTS` と `DJANGO_CSRF_TRUSTED_ORIGINS` を明示する |
| DB 接続 | RDS をプライベートサブネットに配置し、公開 IP で直接公開しない |
| IP 制限 | ALB セキュリティグループで `allowed_cidr_blocks` による接続元 IP 制限を実施 |
| 最小権限 | ECS タスクロール（Web / Scheduled Task）には必要最小限の IAM 権限のみ付与する |
| 外部送信制御 | 自動収集の egress は許可先を限定する（SSRF 対策、5 章参照） |
| HTTPS | CloudFront が HTTPS を終端（TLS 1.2 以上）。ALB は CloudFront からのアクセスのみ受け付ける |
| 機密値管理 | `terraform.tfvars`、Terraform state、`.terraform/` は Git 管理対象外とする |
