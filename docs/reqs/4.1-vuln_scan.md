# 脆弱性診断要件

*作成日: 2026/06/05 ／ 親: [4-sec_req.md](4-sec_req.md)*

---

## 1. 概要

本ドキュメントはドメイン管理システムに対して実施する脆弱性診断の要件を定義する。企業の重要 IT 資産であるドメインの管理情報・リスク情報を扱い、かつ外部へ自動収集アクセスを行うシステムであるため、リリース前および定期的に診断を実施する。

---

## 2. 診断スコープ

| 対象 | 内容 |
|------|------|
| Web アプリケーション | ダッシュボード・台帳・各カテゴリ詳細・棚卸・リスク・承認の全画面 |
| API エンドポイント | REST API（ドメイン CRUD・収集結果登録・履歴取得・マスタ取得） |
| 認証機能 | ログイン・セッション管理・ロールチェック・API トークン認証 |
| バッチ処理 | 自動収集（WHOIS / DNS / CT ログ）・通知・棚卸バッチの実行権限・外部アクセス・ログ出力 |
| 外部アクセス | 自動収集の egress（SSRF・不正応答） |

### スコープ外

- 社内 AD / LDAP サーバー本体（インフラ担当の管轄）
- ネットワーク層の診断（別途実施）
- レジストラ・DNS・CT ログ等の外部サービス本体

---

## 3. 診断タイミング

| タイミング | 診断種別 | 実施者 |
|-----------|---------|--------|
| リリース前（初回） | 脆弱性診断（全項目） | 社内セキュリティ担当 or 外部診断会社 |
| 機能追加・大幅変更時 | 変更箇所を中心とした部分診断 | 同上 |
| 自動収集・外部連携の追加時 | SSRF・外部応答処理を中心とした診断 | 同上 |
| 年1回（定期） | 全項目診断 | 同上 |

---

## 4. 診断項目（OWASP Top 10 準拠）

| # | カテゴリ | 確認内容 |
|---|---------|---------|
| A01 | アクセス制御の不備 | 認可チェックの漏れ・直接 URL アクセスによる範囲外ドメイン閲覧・参照範囲（管理責任部署スコープ）の越境 |
| A02 | 暗号化の失敗 | 通信の平文送信・パスワードの平文保存・Secret のハードコード |
| A03 | インジェクション | SQL インジェクション・XSS・コマンドインジェクション・DNS 名やレコード値経由の注入 |
| A04 | 安全でない設計 | 承認フロー・継承解決・ライフサイクル遷移の業務ロジック欠陥 |
| A05 | セキュリティ設定のミス | デフォルト設定・不要なヘッダー・デバッグ情報（`DEBUG=True`）の漏洩 |
| A06 | 脆弱なコンポーネント | 依存ライブラリの既知脆弱性（Django / dnspython / python-whois / Bootstrap 等） |
| A07 | 認証・識別の失敗 | セッション固定・総当たり攻撃耐性・セッションタイムアウト・API トークンの強度 |
| A08 | ソフトウェアとデータの整合性の失敗 | CSRF・シリアライズ処理・外部収集データの信頼性検証 |
| A09 | セキュリティログと監視の失敗 | 監査ログの欠落・追記専用性の破れ・不正アクセスの検知漏れ |
| A10 | サーバーサイドリクエストフォージェリ | 自動収集（WHOIS / DNS / CT / 連携 API）経由の SSRF・内部 IP / メタデータエンドポイントへのアクセス |

> A10 SSRF は本システムの特性上、重点確認項目とする（外部アクセスを常時行うため）。

## 5. 追加確認項目（業務特性に応じた独自チェック）

| 項目 | 内容 |
|------|------|
| 範囲外ドメインへのアクセス | 利用部門ロールが、自部門の管理単位外のドメイン・履歴・棚卸を API から取得できないことを確認 |
| 論理削除データへのアクセス | `status=deleted` のドメインが通常 API から取得できないことを確認 |
| 履歴・監査ログの改ざん | 変更履歴・監査ログレコードが上書き・削除できないことを確認（追記専用の担保） |
| 承認バイパス | 取得・廃止・移管・管理責任者変更が、承認を経ずに確定できないことを確認 |
| 継承・暫定の越権 | 継承解決により本来権限のない管理単位を更新できないことを確認 |
| SSRF（収集経路） | 収集対象ドメイン名・URL を細工して内部 IP・クラウドメタデータへアクセスできないことを確認 |
| 外部応答の処理 | 過大・不正な WHOIS / DNS / 証明書応答でサービスが異常終了・資源枯渇しないことを確認 |
| 機密情報の非保持 | 証明書秘密鍵・DNS 管理アカウント認証情報が保存・出力されないことを確認 |
| 個人情報・Secret のログ漏洩 | アプリ・バッチログに氏名・メール・認証情報・トークンが出力されないことを確認 |
| バッチの不正実行 | バッチ実行エンドポイント／ジョブが認証なしで呼び出せないことを確認 |
| API トークン | トークンが平文保存されず、再発行で旧トークンが失効することを確認 |

## 6. 合格基準

| 重大度 | 定義 | リリース判断 |
|--------|------|------------|
| Critical | 任意コード実行・認証バイパス・全データ漏洩・SSRF による内部侵入 | 修正完了まで**リリース不可** |
| High | 範囲外データ漏洩・権限昇格・承認バイパス・機密情報漏洩 | 修正完了まで**リリース不可** |
| Medium | 限定的な情報漏洩・CSRF | リリース可（修正計画を明示し次スプリントで対応） |
| Low | セキュリティヘッダー欠落等 | リリース可（バックログに登録して対応） |
| Info | 情報提供・ベストプラクティス推奨 | 対応任意 |

---

## 7. 診断後の対応フロー

```
1. 診断レポート受領
2. 重大度 Critical / High の項目を即時対応
3. 修正内容をセキュリティ担当がレビュー
4. 再診断（Critical / High 項目のみ）
5. 合格後にリリース承認
6. Medium 以下は修正計画を策定しバックログ管理
```

---

## 8. ツール・手法

| 区分 | ツール / 手法 |
|------|-------------|
| 自動スキャン | OWASP ZAP（無償）/ Burp Suite Community |
| 手動診断 | 認証・認可・参照範囲・承認・継承の業務ロジック検証は手動で実施 |
| SSRF 検証 | 収集対象に内部 IP / メタデータ URL / リダイレクトを細工した検証ケースを用意 |
| 依存ライブラリ | `pip-audit`（Python） |
| 静的解析 | Bandit（Python）/ ESLint security plugin（JS） |
