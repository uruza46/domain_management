# 機能要件

*作成日: 2026/06/05 ／ 親: [0-base_req.md](0-base_req.md)*

---

## 1. 本ドキュメントの位置づけ

本ドキュメントは、ドメイン管理システムが提供する業務機能の概要、主要操作、ロールごとの大まかな制御、バッチ処理・外部連携との接続点を定義する。

画面ごとの表示項目、ボタン表示条件、参照範囲、入力バリデーション、エラー表示は [1.1-screen_req.md](1.1-screen_req.md) に記載する。定期実行ジョブ（自動収集・自動チェック・通知）の抽出条件、実行順序、冪等性、通知仕様は [1.2-batch_req.md](1.2-batch_req.md) に記載する。

本システムの基本方針として、属人的かつ人手による運用を可能な限り排除し、情報収集を自動化する（[0-base_req.md](0-base_req.md) 0.2）。したがって各機能は「自動収集された情報をベースに、人は差分・例外・判断のみを扱う」ことを前提に設計する。

## 2. ロール定義と大まかな権限制御

| ロール | グループ | 主な権限 |
|--------|----------|----------|
| システム管理者 | `DOMAIN_SYSTEM_ADMIN` / superuser | 全機能の参照・登録・編集・承認・マスタ管理・権限管理 |
| ドメイン管理責任者 | `DOMAIN_MANAGER` | 全社方針決定、承認、重要リスク判断、全ドメインの横断参照 |
| ドメイン管理担当者 | `DOMAIN_OPERATOR` | 台帳維持、棚卸運用、更新確認、是正対応の起票・追跡、関係者調整 |
| ドメイン利用部門 | `DOMAIN_USER_DEPT` | 自部門が管理責任を負うドメインの用途・担当者・棚卸回答 |
| 知財・ブランド管理担当者 | `DOMAIN_BRAND_MANAGER` | 知財・ブランド保護情報、監視対象、承認否認証跡 |
| DNS・インフラ運用担当者 | `DOMAIN_DNS_OPERATOR` | DNS管理情報、ネームサーバ、DNSSEC等の技術情報確認・更新 |
| セキュリティ運用担当者 | `DOMAIN_SECURITY_OPERATOR` | セキュリティ対策状況、リスク、是正状況の確認・対応 |
| IT資産管理担当者 | `DOMAIN_IT_ASSET_MANAGER` | 他IT資産情報との整合性確認、資産管理台帳との連携 |
| 経営層・マネジメント層 | `DOMAIN_EXECUTIVE` | 重要リスク、未対応事項、全体状況の参照・レポート受領 |
| サービスアカウント | `DOMAIN_SERVICE_ACCOUNT` | API / バッチ経由のシステム連携・自動収集 |

### 2-1. 参照範囲の基本方針

- システム管理者、ドメイン管理責任者、ドメイン管理担当者、経営層、IT資産管理担当者は、画面機能ごとの権限が許す範囲で全ドメインを横断参照する。
- ドメイン利用部門は、自部門が管理責任部署となっている管理単位（登録ドメイン・DNSゾーン・サブドメイン名前空間）の範囲のみ参照・更新できる。
- 管理責任部署は責任継承モデル（[0-base_req.md](0-base_req.md) 0.4.1〜0.4.3）で決まる。個別設定がない場合は上位の管理単位から継承し、最終的に全社ドメイン管理部門を暫定管理責任部署とする。
- 知財・ブランド、DNS・インフラ、セキュリティの各担当は、それぞれの専門領域の情報を全ドメイン横断で確認・更新できる。
- 権限のない画面・操作は 403 を返す。画面上のメニューやボタンもロールに応じて非表示にする。

### 2-2. 管理単位と責任境界

- 管理部署・管理責任者・棚卸・通知は、FQDN 単位ではなく管理単位（登録ドメイン、DNSゾーン、サブドメイン名前空間）に対して設定する。
- サブドメインは検知できたものを原則として管理対象に含め、個別の管理責任が設定されていない限り最も近い上位の管理単位から管理情報を継承する。
- 個別管理対象への昇格は原則として DNSゾーンまたはサブドメイン名前空間単位で行い、個別管理対象の件数増加を抑制する。

## 4. 台帳・ドメイン管理機能（F01-F07, F14）

### 4-1. ダッシュボード表示（F01）

- 全社の管理対象ドメイン数、個別管理対象数、監視対象数を俯瞰できること。
- ドメイン更新期限・証明書有効期限の接近件数を期限の近さ別に表示すること。
- 未対応リスク（テイクオーバー、なりすまし、DNSSEC/DMARC 未設定等）の件数を重大度別に表示すること。
- 棚卸の未回答・期限超過件数、承認滞留件数を表示すること。
- ダッシュボードの各判定は、対応するバッチ（B07 通知、B08 棚卸督促）の業務判定と揃えること。
- 参照範囲が限定されるロール（利用部門）は、自部門が管理責任を負う範囲のみ集計・表示すること。

### 4-2. ドメイン台帳一覧・詳細（F02, F04）

- ドメインをドメイン名、種別、状態、管理区分、対象会社、対象ブランド、管理責任部署、リスク有無で検索・絞り込みできること。
- 管理対象・個別管理対象・継承（個別設定なし）を区別して表示・絞り込みできること。
- 参照範囲はロールに応じて制御すること。利用部門は自部門が管理責任を負う管理単位のみ参照できる。
- ドメイン詳細では、基本情報、レジストラ・契約情報、DNS 管理情報、用途管理情報、知財・ブランド保護情報、セキュリティ対策状況、証明書情報、担当部署・担当者情報、インシデント情報、変更履歴をカテゴリ別に確認できること。
- 自動収集された項目（有効期限、レジストラ、ネームサーバ、主要レコード等）は、取得元と最終取得日時を併せて表示すること。
- 継承で決定された管理情報は、継承元の管理単位を明示すること（個別設定・継承・暫定設定の区別）。

### 4-3. ドメイン新規登録（F03）

- 新規取得時は、取得目的、利用予定、関連ブランド、管理責任者、費用負担、セキュリティ方針、承認者を登録すること（[0-base_req.md](0-base_req.md) 0.6.1）。
- ドメイン名（FQDN）、種別、管理区分、対象会社を必須とすること。
- 管理責任部署・管理責任者は、個別設定または上位管理単位からの継承のいずれかを選択できること。
- 新規取得後のステータスは承認待ちとし、承認機能（F15）に引き渡すこと。
- 自動収集で取得可能な項目（有効期限、レジストラ、ネームサーバ等）は、登録後にバッチ（B01/B02）が補完することを前提に、手動入力を必須としないこと。

### 4-4. ドメイン情報編集（F05）

- 用途、担当者、DNS 設定、レジストラ、証明書、外部委託先等の変更時は、変更内容、変更理由、実施者、承認者、実施日時を記録すること（[0-base_req.md](0-base_req.md) 0.6.3）。
- 各カテゴリ情報の編集権限は領域ごとに制御すること。DNS 管理情報は DNS・インフラ運用、セキュリティ対策状況はセキュリティ運用、知財・ブランド保護情報は知財・ブランド管理を主担当とする。
- DNS 設定変更は事前承認を必須とせず、自動検知または申告に基づき事後確認・差分記録・是正依頼の対象とすること（[0-base_req.md](0-base_req.md) 0.6.3, 0.8）。
- 変更があった情報は、変更がない間の情報をできる限り圧縮しつつ、変更履歴として記録すること（[0-base_req.md](0-base_req.md) 0.5）。

### 4-5. ライフサイクル操作（F06）

- 取得・登録、利用開始、変更、更新、移管、廃止の各段階を管理すること（[0-base_req.md](0-base_req.md) 0.6）。
- 利用開始時は、DNS 設定、公開先、証明書、メール利用、外部サービス連携、監視対象、担当者情報を登録すること。
- 更新時は、有効期限前に更新要否を確認し、更新予定・完了・更新不要判断・費用負担・関係者確認結果を記録すること。
- 移管時は、移管前後の責任者、権限、DNS 影響、証明書影響を記録すること。
- 廃止時は、利用停止確認、DNS 削除・無効化、証明書失効、メール停止、リダイレクト要否、再取得リスク、ブランドリスクを確認し、廃止判断を記録すること。
- 新規取得・廃止・管理責任者変更・レジストラ移管・ブランド保護上重要な判断は、承認機能（F15）の対象とすること。

### 4-6. 管理責任・継承管理（F07）

- 管理単位（登録ドメイン、DNSゾーン、サブドメイン名前空間）ごとに管理責任部署・管理責任者・主担当・副担当を設定できること。
- 個別設定がないサブドメインは、責任継承ルール（[0-base_req.md](0-base_req.md) 0.4.2）に従い上位管理単位から管理情報を継承すること。
- 個別管理対象への昇格条件（NS 委任、外部サービス連携、メール・認証・決済利用、ブランド重要性、運用部署差異）に該当する対象を、個別管理対象として設定できること（[0-base_req.md](0-base_req.md) 0.4.3）。
- 証明書発行・テイクオーバーリスク検知のみを理由とした自動昇格は初期範囲では行わず、リスク確認・通知・是正の対象として扱うこと。
- 管理情報設定区分（個別設定・継承・暫定設定）と継承元管理単位を保持し、画面・履歴で追跡できること。

### 4-7. 変更履歴・監査証跡（F14）

- ドメイン情報、担当者情報、DNS 関連情報、承認状態、リスク評価、是正対応の変更履歴を記録すること（[0-base_req.md](0-base_req.md) 0.10）。
- 手動変更だけでなく、自動収集（B01〜B05）による値の変化も履歴として記録すること。
- いつ、誰が（バッチの場合はサービスアカウント）、何を、なぜ変更したかを確認できること。
- 過去時点の担当者、利用目的、承認状態、リスク状態を追跡できること。
- 参照範囲外のドメインの履歴は参照できないこと。

## 5. 棚卸・リスク・是正（F08, F09）

### 5-1. 棚卸管理（F08）

- 管理対象ドメインおよび個別管理対象のサブドメイン名前空間について、原則として年 1 回の定期棚卸を実施できること（[0-base_req.md](0-base_req.md) 0.7.2）。
- 棚卸では、保有状況、利用状況、管理部署、管理責任者、担当者、更新要否、セキュリティ対策状況、外部サービス連携状況を確認できること。
- 個別管理対象でないサブドメインは、親ドメイン・DNSゾーン・上位サブドメイン名前空間の棚卸に含めて代表確認し、全件個別回答を求めないこと。
- 自動検知された差分、リスク、用途変化、外部サービス連携変化など、確認が必要なものを都度確認の対象とすること。
- 棚卸・都度確認の依頼、回答状況、確認結果、未回答、差戻し、是正要否を記録すること。
- 未回答または期限超過は通知・エスカレーションの対象とすること（B08）。
- 確認状態（確認済、確認依頼中、未回答、差戻し、要是正、廃止候補等）を管理すること。

### 5-2. リスク確認・是正対応管理（F09）

- 失効リスク、設定不備、サブドメインテイクオーバーリスク、なりすましリスク、ブランド毀損リスク、担当者不在リスクを確認できること（[0-base_req.md](0-base_req.md) 0.7.4）。
- 自動チェック（B03/B04/B05）が検出したリスクと、手動で起票したリスクを一元管理すること。
- 検出された不備やリスクについて、対応方針、担当者、期限、対応状況、完了確認結果を管理すること（[0-base_req.md](0-base_req.md) 0.7.5）。
- 是正期限超過は通知・エスカレーションの対象とすること（B07）。
- 将来的にはリスク評価のスコアリングにより是正対応の優先順位付けを行うことを検討する（[0-base_req.md](0-base_req.md) 0.14）。

## 6. 技術・セキュリティ情報（F10, F11）

### 6-1. セキュリティ対策状況管理（F10）

- DNSSEC、レジストリロック、レジストラロック、MFA、権限管理、サブドメインテイクオーバー対策、期限切れ証明書対策、メールなりすまし対策の実施状況を管理すること（[0-base_req.md](0-base_req.md) 0.5.6）。
- 自動チェック可能な項目（DNSSEC、ロック状況、テイクオーバー、SPF/DKIM/DMARC、期限切れ証明書）はバッチ（B04）の結果を反映し、手動確認が必要な項目は担当者が更新すること。
- 対策未実施・不備の項目はリスク（F09）として是正対応に接続すること。

### 6-2. 証明書管理（F11）

- 証明書の発行先ドメイン、発行者、有効期限、発行方式、更新方式、利用システム、管理担当（ML 可）、失効予定、CT ログ検知結果を管理すること（[0-base_req.md](0-base_req.md) 0.5.7）。
- CT ログ監視（B03）で検知した証明書を台帳と突合し、未把握の証明書発行を検知できること。
- 有効期限接近・失効予定は通知（B07）の対象とすること。
- 期限切れ証明書はセキュリティ対策状況（F10）・リスク（F09）に接続すること。

## 7. 監視・インシデント（F12, F13）

### 7-1. 監視対象管理（F12）

- 自社ブランド名、サービス名、商標、略称等を含む、把握・監視すべき候補ドメインを監視対象として管理すること（[0-base_req.md](0-base_req.md) 0.3.1）。
- 監視対象は保有・利用・契約・DNS 管理情報等を必須管理項目とせず、検知結果、確認状況、対応判断、対応履歴を管理すること。
- 類似ドメイン・なりすましドメインのスキャン（B05）が検知した候補を監視対象に取り込めること。
- 監視対象が自社で取得・利用する判断に至った場合は、管理対象ドメイン（F03）へ昇格できること。

### 7-2. インシデント・トラブル管理（F13）

- インシデントの発生日時、内容、影響範囲、対応状況、再発防止策を管理すること（[0-base_req.md](0-base_req.md) 0.5.9）。
- インシデント情報をドメインのリスク評価や是正対応の優先順位付けに活用できること。
- インシデントは対象ドメインまたは管理単位に紐付けて記録すること。

## 8. 承認機能（F15）

### 8-1. 承認対象

- 新規取得、廃止、管理責任者変更、レジストラ移管、ブランド保護上重要な判断を承認対象とする（[0-base_req.md](0-base_req.md) 0.8）。
- DNS 設定変更は承認対象に含めず、事後確認・通知・是正対応の対象とする。

### 8-2. 承認操作

- システム管理者・ドメイン管理責任者は全社の承認申請を承認できる。
- ブランド保護上重要な判断は、知財・ブランド管理担当者の確認・否認証跡を必要とする（[0-base_req.md](0-base_req.md) 0.5.5）。
- 承認・否認の結果と証跡を変更履歴に記録する。
- 否認時は理由コメントを必須とする。表示形式・エラー表示は画面要件に定義する。

## 9. 通知・アラート（F16）

- 以下の事象を画面のアラート・ダッシュボードに表示すること（[0-base_req.md](0-base_req.md) 0.9）。
  1. ドメイン更新期限の接近
  2. 証明書有効期限の接近
  3. 担当者未設定または担当者情報の陳腐化
  4. DNS 設定の不整合または危険な設定
  5. サブドメインテイクオーバーの可能性
  6. DNSSEC、DMARC 等の重要対策の未設定
  7. 類似ドメイン、なりすまし、ブランド毀損につながる可能性の検知
  8. 棚卸未回答、是正期限超過、承認滞留
- 画面上のアラート表示はオンライン処理で行い、メール等の外部通知は B07 のバッチ要件として扱う。
- 通知判定は対応するバッチの抽出条件と業務的に揃えること。

## 10. 外部連携・データ取込（F17）

- レジストラ／ドメイン管理サービス、DNS 管理サービス、証明書管理・CT ログ監視、IT 資産管理、ID 管理・組織／社員／所属マスタ、ワークフロー・承認、メール／チャット／チケット、セキュリティ診断・ASM・脆弱性管理と必要に応じて連携すること（[0-base_req.md](0-base_req.md) 0.11）。
- 初期段階ではすべての外部連携を必須とせず、手動登録、CSV 取込、定期バッチ、自動 API 連携を段階的に選択できること。
- CSV 取込は全行検証後に登録し、1 行でもエラーがあれば全体を登録しないこと。
- 機密情報そのもの（証明書秘密鍵、DNS 管理アカウント認証情報等）は保持せず、保管先や管理責任者のみを管理すること（[0-base_req.md](0-base_req.md) 0.3.2, 0.12）。

---

## 11. 権限・マスタ管理（F18）

- 利用者の役割に応じて、閲覧・登録・変更・承認・削除・是正完了確認の権限を制御すること（[0-base_req.md](0-base_req.md) 0.8）。
- ロール、部署・担当者マスタ、管理単位、通知設定、監視対象キーワードを管理できること。
- 連絡先は個人メールではなく、可能な限りグループメールまたはチーム連絡先を管理すること（[0-base_req.md](0-base_req.md) 0.5.8）。
- 組織・社員・所属情報は外部連携（B09）で同期することを基本とし、手動メンテナンスを併用すること。

---

## 12. API 連携

- サービスアカウントは API 経由でドメイン情報・収集結果を参照・登録できる。
- 自動収集バッチ（B01〜B05）は内部処理として実行するか、サービスアカウントの API 経由で結果を登録する。
- API 認証はハッシュ化サービストークンを用いる。
- API の既定権限は認証済みユーザーのみとする。
- API のページングは 50 件単位を既定とする。
- トークン発行系の操作はレート制限（`5/min`）を行う。
