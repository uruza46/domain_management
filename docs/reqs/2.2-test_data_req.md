# テストデータ要件

*作成日: 2026/06/05 ／ 親: [2-data_design.md](2-data_design.md)*

---

## 1. 概要

本ドキュメントは、ドメイン管理システムの開発・テスト・デモで使用するテストデータの構成を定義する。

テストデータの正は、Django 管理コマンド `seed_data` とする。

- 実装: `app/domains/management/commands/seed_data.py`
- 実行例: `python manage.py seed_data`
- テスト: `app/domains/tests/test_seed.py`

`seed_data` は冪等に実行できる。既に対象データが存在する場合は追加投入せず、既存データを維持する。

### テスト方針

`seed_data` はデモ・受け入れ確認・画面確認のための大規模データ投入を担う。pytest の単体テストおよびビュー回帰テストでは、原則として `testsupport.factories` の最小データを利用する。

理由:

- テスト実行時間を安定させる。
- `seed_data` のデータ分布変更で無関係なビュー回帰テストが壊れることを防ぐ。
- 参照範囲（管理責任部署スコープ）と継承解決の境界条件をテストごとに明示する。

例外として、`domains/tests/test_seed.py` は `seed_data` 自体の受け入れ確認であるため、`call_command('seed_data', '--quiet')` を使用する。

外部依存（WHOIS / DNS / CT ログ等の自動収集）はテストでは実ネットワークへアクセスせず、固定のスタブ／フィクスチャを使用する。

## 5. 部署・社員・所属マスタ

### 部署

- 本部 5 件（`HB01`〜`HB05`）、その配下に部 25 件（`BU01`〜`BU25`）を作成する。
- 各部署に `parent_code`、`honbu_code`、`level`、`start_at` を設定する。`HB01`〜`HB05` は level=2 とし、`honbu_code` は自部署を指す。
- 全部署の `is_active` は `True` とする。

| 部署コード | 本部名 |
| --- | --- |
| HB01 | 情報システム本部 |
| HB02 | コーポレート本部 |
| HB03 | 事業推進本部 |
| HB04 | 知財・法務本部 |
| HB05 | セキュリティ本部 |

### 社員

| 項目 | 内容 |
| --- | --- |
| 件数 | 100 件 |
| 社員番号 | `EMP001` から `EMP100` |
| メールアドレス | `emp001@example.com` 形式 |
| 氏名カナ | 姓名リストから生成し、カナ項目も設定 |
| 電話番号 | `03-0000-0001` 形式 |
| 在籍フラグ | 全員 `is_active=True` |

- 氏名生成は [2.2-test_data_req.md（picsy）](../../../picsy/docs/reqs/2.2-test_data_req.md) と同方式の姓名リストを用い、`random.seed(42)` で固定する。
- 管理責任者・主担当・副担当・DNSゾーン管理者には、各本部の社員を割り当てる。

### 所属情報

- 全社員に本務所属を 1 件ずつ作成する。
- 10 名には兼務所属を 1 件追加し、兼務を含む所属本部スコープを検証できるようにする。
- 所属情報は `employees2departments` に作成し、社員マスタには部署コードを保持しない。

## 6. 管理単位と継承

### 構成

| 単位種別 | 件数 | 設定区分の内訳 |
| --- | ---: | --- |
| registered_domain（登録ドメイン） | 20 | 個別設定 18、暫定設定 2 |
| dns_zone（DNSゾーン） | 8 | 個別設定 8 |
| subdomain_namespace（サブドメイン名前空間） | 12 | 個別設定 6、継承 6 |

### 作成ルール

- 登録ドメイン 20 件はそれぞれ管理単位を持ち、本部・管理責任者を割り当てる。
- 暫定設定 2 件は管理責任部署を全社ドメイン管理部門（`HB01`）とし、`setting_type='provisional'` とする。
- 継承の管理単位は `setting_type='inherited'`、`inherited_from_unit_id` に上位登録ドメインの管理単位を設定する。
- 個別管理対象化理由（`promotion_reasons`）は、NS 委任・外部サービス連携・メール利用等を分散して付与する。
- 棚卸状態（`check_status`）と `next_check_at` を分散させ、未回答・期限超過・確認済を再現する。

## 7. ドメイン台帳

### 構成

| 区分 | 件数 | 内容 |
| --- | ---: | --- |
| 登録ドメイン | 20 | gTLD / ccTLD を混在（`.com` / `.co.jp` / `.jp` / `.net`） |
| サブドメイン | 280 | 各登録ドメイン配下に 5〜20 件 |

### 作成ルール

- 登録ドメイン名は `example.com` `exampleshop.com` `examplepay.jp` `example.co.jp` 等、ブランドに対応させる。
- サブドメインは `www` `mail` `api` `shop` `pay` `recruit` `dev` `stg` 等を組み合わせて生成する。
- `domain_type` は登録ドメインを `gtld`/`cctld`、配下を `subdomain` とする。
- `mgmt_category` は原則 `managed`、個別管理対象化理由を持つ管理単位配下は `individual` とする。
- `status` は分散させる（下表）。
- `expires_at` は分散させ、一部を 30 日以内・60 日以内・90 日以内・超過に設定して期限通知（B07）を再現する。
- 自動収集対象項目（`expires_at`, `registrar_name`, `name_servers` 等）には `collected_at` を設定する。

### ステータス分布

| ステータス | 件数 | 用途 |
| --- | ---: | --- |
| `active` | 285 | 利用中 |
| `pending` | 5 | 承認待ち（新規取得申請） |
| `expired` | 6 | 失効疑い |
| `deleted` | 4 | 廃止済み |

## 8. レジストラ・DNS・証明書

### レジストラ・契約

- 登録ドメイン 20 件に契約情報を付与する。
- レジストラ名は `Example Registrar` `Onamae` `GoDaddy` `Google Domains` 等を分散する。
- `renewal_deadline` を分散し、一部を更新期限接近に設定する。
- `transfer_allowed` は混在させる。

### DNS 管理情報・レコード

- 各ドメインに DNS 管理情報を 1 件付与する。
- `dnssec_enabled` を混在させ、`spf_status` / `dkim_status` / `dmarc_status` を `set` / `unset` / `invalid` で分散する（なりすまし対策リスクの再現）。
- DNS レコードは A / CNAME / MX / TXT を中心に各ドメイン 1〜5 件作成する。
- 一部のサブドメインに、参照先が削除済みの CNAME を作成し、テイクオーバー疑いを再現する。

### 証明書

- 120 件作成する。うち 5 件は `ct_detected=True` かつ `domain_id=NULL`（台帳未把握）とする。
- `expires_at` を分散し、一部を有効期限接近・超過に設定する。
- `issue_method` は `acme` / `manual` / `outsourced` を分散する。

## 9. リスク・棚卸・監視・インシデント・承認

### リスク・是正対応

- 60 件作成し、`risk_type` と `severity` を分散する。
- `status` は `open` / `in_progress` / `confirming` / `closed` を分散し、一部を `due_at` 超過に設定する。
- テイクオーバー疑い・期限切れ証明書・DNSSEC 未設定・なりすまし対策不備を必ず含める。

### 棚卸

- 管理単位ごとに 1 件、計 40 件を作成する。
- `inventory_type` は `periodic` を中心に、一部 `adhoc`（自動検知差分あり）を作成する。
- `check_status` を分散し、未回答・期限超過・差戻し・要是正・確認済を再現する。

### 監視対象

- 25 件作成し、`detection_type` を `similar` / `spoofing` / `trademark` / `other` で分散する。
- `confirm_status` と `action_judgment` を分散し、未確認・対応判断済を再現する。
- 1〜2 件は「管理対象へ昇格」検証用に取得検討（`acquire`）とする。

### インシデント

- 8 件作成し、過去のテイクオーバー・なりすまし・失効等を再現する。
- 一部を関連リスク・対象ドメインに紐付ける。

### 承認

- 10 件作成する。`pending` 3（取得・廃止・移管）、`approved` 5、`rejected` 2。
- ブランド重要判断を 1 件含め、`brand_reviewed_by` を設定する。

## 10. 変更履歴

- 各主要レコード（ドメイン・管理単位・証明書・リスク等）の作成時に `新規登録` 履歴を 1 件作成する。
- 一部のドメインに `自動収集更新`（`source='auto'`、`changed_by='collector'`）の履歴を作成し、手動変更と自動収集の区別を画面で確認できるようにする。
- 承認・棚卸・是正の各シナリオに対応する履歴を作成する。
- 変更履歴は追記専用であり、更新・削除しない。

## 11. テストシナリオ向けデータ条件

| シナリオ | 必要データ | 作成方法 |
| --- | --- | --- |
| ダッシュボード表示 | 期限接近・リスク・棚卸・承認 | 各分布を持つデータを投入 |
| 期限接近通知 | `expires_at` が 30/60/90 日以内のドメイン | ドメイン・証明書の期限を分散 |
| テイクオーバー検知 | 参照先削除済み CNAME | 一部サブドメインに作成 |
| なりすまし対策不備 | SPF/DKIM/DMARC `unset` | DNS 管理情報で分散 |
| CT 未把握証明書 | `ct_detected=True` かつ `domain_id=NULL` | 証明書 5 件を未把握で作成 |
| 継承表示 | `setting_type='inherited'` の管理単位 | 継承 6 件を作成し継承元を設定 |
| 暫定管理責任 | `setting_type='provisional'` | 暫定 2 件を全社ドメイン管理部門に設定 |
| 棚卸未回答・督促 | `check_status='unanswered'` かつ期限超過 | 棚卸状態を分散 |
| 承認一覧 | `status='pending'` の承認 | 承認 3 件を pending で作成 |
| 監視対象昇格 | 取得検討の監視対象 | `action_judgment='acquire'` を作成 |
| 参照範囲制御 | 異なる管理責任部署のドメイン | 本部別に管理単位を割当 |

## 12. データ管理方針

- テストデータの正は `seed_data` 管理コマンドとする。
- ドキュメントと seed 実装が食い違う場合は、まず seed 実装と受け入れテストを確認する。
- 自動収集（WHOIS / DNS / CT ログ）はテストで実ネットワークへアクセスせず、固定スタブを使用する。
- 機密情報そのもの（証明書秘密鍵、DNS 管理アカウント認証情報）はテストデータにも含めない。
- 本番データとは混在させない。
- デモ環境・テスト環境では `python manage.py seed_data` で投入する。
- 既存データがある場合、`seed_data` は同種データを再作成しない。
